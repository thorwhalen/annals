annals.overview#

Spoken overviews of a document: the request a page makes, and the worker that fulfils it.

A reader asks for an overview from a document’s page. That writes one small JSON file under the data root (overviews/<doc id>.json). A worker on the same machine reads the document from the store, runs a command that makes the overview, and publishes the result as a document of its own. The page polls the request’s state.

annals does not know how an overview is made. The command is the seam: any program that takes a text file and writes one HTML page, named in ANNALS_OVERVIEW_COMMAND or passed to work(), with {source}, {minutes} and {out} filled in, and {url}, the source document’s page, so the overview can link to what it was based on:

my-overview {source} --minutes {minutes} --player-to {out} --source-url {url}

The feature is off unless the host turns it on (mk_api(overviews=True)), because making an overview spends money. A host can also offer it to some readers only (mk_api(overviews={"me@example.com"}), or ANNALS_OVERVIEWS for annals.api.mk_app(); see readers_offered()): the others get no Listen button, and the documents the feature makes (made_here()) are hidden from them. For the same reason, a current overview is not made again unless forced, a crash after publishing does not pay twice, work stops at a daily limit, and a request nobody fulfilled expires rather than spending money whenever a worker next wakes.

Run the worker on a timer. Finished request files stay in the folder and the worker writes there, so a watcher on the folder would keep waking it.

When the command cannot work until someone acts (an expired login, a voice account out of credit), pressing again only spends the daily limit. So the worker notices it: the same failure, fast, from two documents in a row, marks the maker down with that reason (a document failing twice is that document). An agent can mark it too, with a link to where it is being fixed (annals listen-down "why" --link URL). While it is down, nothing fails or is dropped: requests wait (past the daily limit too), the page says why and what to do instead of offering a Try again, and the worker tries one of them again every few hours. The first success, or annals listen-down --clear, clears the mark and queues everything that waited.

>>> html_to_text("<title>x</title><p>One &amp; two</p><script>no()</script><p>Three</p>")
'One & two\n\nThree'
>>> [c["characters"] for c in choices()]
[2700, 4500, 6300]

annals.overview.readers_offered(spec)[source]#

Who may ask for and hear overviews: False (nobody), True (every reader), or a test.

spec is what a host passes as overviews: a bool, a predicate on the reader’s name (an email, as annals.api.reader_of() gives it), a collection of names, or a string as ANNALS_OVERVIEWS holds it (names separated by commas, * for every reader, empty for nobody; true/1/yes and false/0/no mean the same as * and empty, never a reader so named). Names are compared without case.

>>> readers_offered("*"), readers_offered(""), readers_offered(None)
(True, False, False)
>>> readers_offered("true"), readers_offered(" No "), readers_offered(["*"])
(True, False, True)
>>> may = readers_offered(" Me@Example.com, ")
>>> may("me@example.com"), may("someone@example.com")
(True, False)

annals.overview.work(store, requests, *, command=None, timeout=1800, daily_limit=None, doc_url=<class 'str'>)[source]#

Fulfil every queued request, one at a time, until none is left; return what happened.

A failure is recorded on its request, for the page to show, and the next one still runs. A request made while this runs is picked up before it exits. doc_url turns a document id into its page, for {url}. While the maker is down, requests wait, and one of them is tried every PROBE_EVERY_S; once one works, those waiting run too.

Return type:

list[dict]
